# Maintain a verification skill

A feature map rots as soon as the app changes. This skill is the upkeep loop for a skill generated by `/skill:create-verification-skill`, or any project-local verification skill with a feature map. The unit of rigor is the feature, not every sentence. Cover every feature file from source and exercise every feature live, without proving every bullet in a terminal.

## Outcomes

Pick one, and say which:

- **clean:** every feature got source and live coverage, and nothing is worth shipping. No branch, no PR.
- **changed:** one PR ships proven doc, harness, or map corrections.
- **blocked:** coverage could not finish, or a proven fix could not ship safely. Say exactly what blocked it.

## Edit scope

Edit only the verification skill's own directory: its `SKILL.md`, `features/`, and any harness scripts it owns. Never edit product code during a run. When the app no longer does what the map describes, decide whether it is doc drift or a product regression. Fix doc drift in the map. Report a regression; do not paper over it in docs.

## Pass

0. **Locate the target.** Find the project-local skill with launch and drive sections and a feature map, usually `.agents/skills/verify-*/`. If several match, ask which one. If none match, stop and point at `/skill:create-verification-skill` instead of inventing a target.

1. **Index hygiene.** Read the feature map README and glob its sibling files. Fix missing, extra, duplicate, or dead entries. Keep this light; do not generate an inventory.

2. **Source wave.** Launch read-only subagents concurrently to cover every feature file. Use one subagent per feature file; when the map has many files, batch small or related ones so the wave stays at about six subagents. Each explains how its features work from source, flags likely doc drift with citations, and returns one concise live-verification recipe per feature. Subagents never drive the app and never edit files. Return shape per feature: summary, source entry points, likely drift or none, one recipe.

3. **Reconcile.** Confirm every feature file has a returned summary. Merge overlapping recipes into as few app states as practical. Spot-check cited drift; do not re-prove clean claims. Sweep recent churn for user-facing surfaces missing from the map. Call one missing only with a concrete source path.

4. **Live pass.** Required even when source looks clean. The coordinator does all driving. Follow the verification skill's launch model: one long-lived instance driven serially for servers and UIs, or a fresh isolated session per drive for short-lived CLIs. The skill's Launch section decides, not this one. Exercise every feature at least once.

   Hold these invariants for the whole pass, whatever fails:

   - **Health before driving.** Run doctor before the first drive, on each fresh session when sessions are the unit, and after any failed drive. When doctor cannot see the failure, such as a wedged UI on a healthy process, reset to a known state or relaunch.
   - **Evidence survives.** Evidence captured so far survives every cleanup. Check it at its named location; do not assume.
   - **No residue.** Nothing a drive started outlives its usefulness. Clean failed-iteration residue whether the session is stuck, exited, or shared. For a shared instance, clean the residue, not the instance.

   A doctor failure caused by skill drift is drift. Fix it within edit scope and retry once, restarting only what the fix invalidated, before calling the pass `blocked`. Mark a feature `verified-unreachable` only with the concrete prerequisite (auth, entitlement, OS, external state) and the route attempted. If the map omits that prerequisite, that is drift.

   Re-drive every harness fix from triage before it ships. Do final teardown after the last drive, including those re-proofs, so nothing outlives the run. Evidence stays, per the skill.

5. **Triage.**
   - Wrong or missing user-POV description: doc drift. Fix it.
   - Working behavior the harness cannot drive: harness gap. Fix it. Follow the generation helpers rule: scripts are executable and their invocation is documented in the skill body.
   - App behavior that is actually broken: product gap. Record it for the user and keep it out of this PR.

6. **Ship or stop.** For `changed`, open one PR of proven corrections after re-reading every changed file. For `clean` or `blocked`, open no PR; report the outcome and coverage honestly.

Keep concise run notes in a scratch location: features covered, unreachable prerequisites, confirmed drift, outcome. Do not commit them.
